## Benchmark score

The benchmark currently has two scoring layers:

1. **M1 scenario catalog** — 9 vulnerable scenarios and 2 controls.
2. **Full planted norm set** — 34 violated norms and the same 2 controls.

The existing production scorer uses the M1 catalog. Its semantic mode matches
generated norms by action/effect coverage rather than requiring the model to
invent the benchmark's exact norm identifiers.

| Metric | Value |
|---|---:|
| Vulnerable scenarios | 9 |
| Found vulnerable scenarios | 7 |
| Recall | 77.8% |
| Controls | 2 |
| False positives on controls | 0 |
| Distinct scored findings | 45 |
| Precision | 15.6% |
| Unexpected findings | 38 |

`Distinct scored findings` is the scorer's precision denominator: 47 raw
finding events collapse to 45 because two generated invariant identifiers were
raised twice. The scorer counts the 38 unexpected identifiers once each.

### Strict effect score

All 47 raw findings had the generic effect `allowed(action)`. None carried a
specific `reached`, `changed`, `external_call`, `duration`, or `has` effect.
Therefore the 7/9 M1 result is the scorer's action-coverage interpretation,
not proof that all seven specific planted effects were observed.

Strict canonical-effect matching over the full planted norm set gives:

| Metric | Value |
|---|---:|
| Full vulnerable norms | 34 |
| Exact effect matches | 4 |
| Strict recall | 11.8% |

The exact matches were:

- `norm:bola-order-read`
- `norm:fla-admin-delete`
- `norm:stf-uncancel`
- `norm:stf-dispatch-twice`

For reference, applying the same broad action-coverage rule to all 34 planted
norms recovers 14/34 (`41.2%`), but that number has the same generic-effect
caveat as the M1 7/9 result.

## Interpretation

This is a valid full-engine run, not a unit-test simulation: it used the real
Neo4j projection, real local gRPC target, real LLM semantic compiler, real
planner, real differential comparator, and real deterministic finding
evaluation.

The main positive result is recall on the original M1 vulnerable scenarios:
7 of 9 were discovered from a clean semantic layer. The two controls were not
converted into false positives.

The main negative result is precision. Most generated findings came from
authorization/elevation norms for methods outside the original M1 answer key.
Those findings are deterministic and grounded, but the benchmark currently
classifies them as unexpected. Before comparing with Nuclei or an LLM-only
agent, the benchmark needs either:

1. an explicit expected-noise catalog for non-M1 methods, or
2. a product policy that suppresses generic permission-required norms unless
   the scenario also demonstrates an unauthorized security-relevant effect.

The two missed scenarios indicate remaining blind spots:

- `disclose-user-email` requires linking an output field to a sensitive
  resource field and proving exposure without an explicit benchmark-provided
  field-role answer.
- `path-traversal-doc` requires a traversal payload/oracle chain that was not
  generated from the clean LLM semantic layer in this run.

## Reproduction

```sh
# Neo4j and benchmark gRPC server must be running locally.
export CPA_NEO4J_URI=bolt://localhost:7687
export CPA_NEO4J_USER=neo4j
export CPA_NEO4J_PASSWORD_FILE=/path/to/neo4j_password
export NEO4J_PASSWORD_FILE="$CPA_NEO4J_PASSWORD_FILE"

export CLOUD_DAST_DESCRIPTOR_SET="$PWD/benchmarks/nsfy-bench/gen/desc.binpb"
export CLOUD_DAST_MODEL_TOKEN_FILE=/path/to/model_token
export CLOUD_DAST_TOKEN_ATTACKER=bench:attacker
export CLOUD_DAST_ALLOWED_IDENTITIES=attacker
export CLOUD_DAST_GRPC_INSECURE=1

export CLOUD_DAST_DIFF_MODE=1
export CLOUD_DAST_DIFF_MODES=factors,payload,readback

.venv/bin/python -m benchmarks.nsfy_bench.stand load --fresh
.venv/bin/python -m benchmarks.nsfy_bench.stand serve --address 127.0.0.1:50051

.venv/bin/python -m cloud_dast.composition.live_cli \
  --profile benchmarks/nsfy-bench/profiles/nsfy-bench-llm.toml \
  --refresh-grounding \
  --event-log /tmp/nsfy-e2e.jsonl
```
