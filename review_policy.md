# Code review policy

Ревью проверяет не только корректность, но и стоимость абстракций.

Для каждого нового типа, класса и публичной функции reviewer обязан ответить:

1. Какое наблюдаемое поведение это добавляет?
2. Есть ли реальный consumer и execution path в текущем пакете?
3. Можно ли выразить тот же контракт меньшим количеством типов, полей или
   переходников?
4. Не дублирует ли новая модель уже существующую (`MethodSpec`/`OperationSpec`,
   `EndpointLayer`/`AccessSurface`, `Target`/`TransportAdapter`)?
5. Не добавляет ли compatibility API только видимость прогресса, не обеспечивая
   миграцию и тест обратной совместимости?

Reviewer возвращает работу worker-у, если обнаруживает:

- мёртвый контракт, который нигде не вызывается;
- adapter или policy, существующий только как тип без runtime path;
- две модели одного понятия без ясной границы владения;
- wrapper/accessor без самостоятельного поведения;
- длинную функцию, которую можно разделить по use case boundary;
- ручную реализацию библиотечного примитива без измеримой причины;
- тесты, проверяющие форму объектов вместо наблюдаемого поведения;
- новые поля или слои, добавленные «на будущее» без текущего потребителя.

Каждое замечание должно содержать конкретное упрощение: удалить, объединить,
перенести к consumer-у, подключить в execution path или отложить до отдельного
пакета. Reviewer не принимает церемонию ради церемонии под видом extensibility.
